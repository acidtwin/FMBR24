## Save system (session 14, `fm_editor/savefile.py`)

- Flow: Make HGP / Make HGC patch the in-memory `game_db.dat` only (no dialog for a file name, instant, sets `_dirty`, `_pending`); **Save Changes** (enabled only when dirty) -> `SaveWorker` -> `save_in_place`: build `<save>.fm.tmp` (same folder), verify it by re-opening (member list, sha256 of every unmodified raw member vs the original, decompressed `game_db.dat` == in-memory buffer), then back up, then `os.replace` over the original. Any failure before the replace removes the temp and leaves the original byte-identical.
- Backups: `<save>.fm.bk1` = the file as it was immediately before this save; `<save>.fm.bk2` = previous bk1 (rename rotation). First save (no bk1): bk1 AND bk2 are copies of the original, so the pristine original survives until the 3rd save. Names end `.bk1/.bk2` (not `.fm`) so FM24's Load Game list does not show them; to use one in FM24 copy it into the saves folder and drop the suffix. Old-style `bk1-<name>.fm` is recognised as the previous bk1 (becomes bk2) and left alone. Every copy is fsynced and re-read (size + sha256). Free-space check: 3x file size on first save, else 2x (+16 MB).
- File changed on disk since load (size/mtime sig in `save_data['disk_sig']`, set in `_reload_save`/`_finish_load`) -> Save is refused (offsets in memory would be wrong). After a successful save the archive layout in `save_data` (members/header/index_marker, `disk_sig`) is refreshed from the new file; before this fix a second in-place save would have read members at the old offsets.
- HGC insertion (`patch_to_hgc` adds a 16-byte record) shifts every later offset: `save_data['offsets_stale']` blocks further patches until Save + Reload. HGP patches are in place. The Players/Reports rows built at load keep the old HGP flag until Reload (only the Squad table is refreshed).
- Dirty guards: Reload asks "Discard unsaved changes?" (Discard/Cancel); Load another save and window close ask Save / Discard / Cancel (Save runs the save, then continues via `_after_save`); close is refused while a save runs. The parse cache (path+mtime keyed) is cleared after a save; `load_cache` is still never called.
- Tests: `tests/test_savefile.py` (synthetic archive: rotation, failure injection, stale file, no space, legacy names). Verified headlessly on a scratchpad COPY of a real save (patch -> save -> backups on disk -> Reload shows patched flags; HGC insert + reload).
- Not verified: FM24 actually loading an overwritten save (only our own re-parse); save time on the user's machine.

Ability block `names_end+57` (CA `b[at-38]`, attrs `b[at..at+54]`); personality `b[end+17..end+25]`; HGP `b10=0x08,b11=0x46`; HGC `b10=0x01,b11=0x48` (bytes0-3 = club entity id = club_id+1); injury `b11=0x47` (trail byte0 = days); contract `b10=0x01,b11=0x6a` (byte13=year-2000, byte14=month); coaching magic `XX 1a ea 07` at records_end+10 (CA magic+33, PA magic+35, Section B magic+81 14 bytes /5, Section A extras magic+37+33/36/39); club staff arrays = flat u32 PID arrays, byte before count == 0x00.
